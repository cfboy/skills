(email + password, passkeys, organizations) · Supabase Postgres with Row Level
Security · Drizzle (schema and migrations) · shadcn/ui on Tailwind v4 ·

GitHub Actions → Supabase migrations → Vercel.

## How a request is decided

1. **Who** — BetterAuth verifies the session cookie (`lib/auth/session.ts`).
{{#multi}}
2. **Where** — the organization is named by the route (`/orgs/[orgId]`) or the
   action's input, never remembered in the session. `orgScope(orgId)`
   (`lib/org-scope.ts`) checks membership and returns the role and a client.
{{/multi}}
{{#single}}
2. **Where** — this is a single-organization app: the organization is the
   deployment and never appears in the URL. Pages resolve it from the
   person's membership (`membershipsOf`), actions receive its id, and
   `orgScope(orgId)` (`lib/org-scope.ts`) checks membership and returns the
   role and a client. The data model and RLS are the multi-tenant ones, so
   becoming multi-tenant later is a routing change: move pages under
   `/orgs/[orgId]` and add an organization picker.
{{/single}}
3. **What** — that client carries a 5-minute ES256 JWT minted for this person
   in this organization (`lib/supabase/sign-token.ts`). Every read and write
   goes through supabase-js with it, and **RLS decides**. `current_org_id()`
   re-checks the token's organization against `member` on every statement.

## Rules that are not negotiable

- **App reads and writes go through supabase-js with the person's token.**
  The Drizzle pool (`db/`) connects as the database owner, which RLS does not
  apply to: it is for BetterAuth, for identity lookups RLS itself needs
  (memberships), and for scripts. Never for domain reads or writes in a page or
  action.
- **The service-role client (`lib/supabase/admin.ts`) is for scripts only.**
  ESLint refuses it under `app/`, `actions/` and `components/`.
- **Every tenant table has `org_id`, RLS on, and hand-written policies** in a
  custom migration — never generated by drizzle-kit, which drops `USING` /
  `WITH CHECK` from `FOR ALL` policies. Each policy gets an assertion in
  `scripts/rls-check.ts` in the same change. RLS failures are silent; that
  script is the only evidence they work.
- **Permissions are asked, not compared.** `scope.can({ note: ["delete"] })`,
  never `role === "admin"` in a screen. `lib/auth/permissions.ts` and the SQL
  helpers (`is_org_admin()`) must agree.
- **Server Actions return `ActionResult`.** Expected failures are values with a
  message for a person, not throws. Parse input with zod — it is `unknown`.
- **TanStack Form `Subscribe` selectors return one primitive.** ESLint enforces
  it; an array or object selector renders nothing in production.
- **Environment through `serverEnv()`** (`lib/env.ts`), never `process.env.X!`.

## Adding a table

1. Describe it in `db/schema/<area>.ts` with `orgId` (`restrict`), export it
   from `db/schema/index.ts`.
2. `pnpm db:generate --name=<what>` for the table.
3. `pnpm db:custom --name=<what>_behaviour` and write in it: `enable row level
   security`, its policies against `current_org_id()`, triggers
   (`set_updated_at`), any function.
4. `pnpm db:reset && pnpm db:types` — the migrations apply from scratch and
   `lib/database.types.ts` follows.
5. Add the table's assertions to `scripts/rls-check.ts`: who reads, who
   writes, that another organization sees nothing, that a row cannot be moved
   between organizations.
6. Then the permission in `lib/auth/permissions.ts`, the action in
   `actions/`, the screen in {{#multi}}`app/(app)/orgs/[orgId]/…`{{/multi}}{{#single}}`app/(app)/…`{{/single}}.
7. Add its user path to the verification map (below).

## Commands

```bash
pnpm dev:setup      # first time: signing key, Supabase stack, .env.local, types, dev logins
pnpm dev            # http://localhost:3000
pnpm check          # lint + types + unit tests — before every commit
pnpm verify         # check + db:rls-check — before every pull request
pnpm db:reset       # rebuild the local database from migrations (wipes dev logins:
                    # `pnpm dev:accounts` puts them back)
```

## Verifying in the browser

Tests and `pnpm verify` prove the database and the code; they do not prove a
person can do the thing. That is the project's verification skill,
`.claude/skills/verify-__APP_SLUG__/`:

- It is created once with pstack's **`create-verification-skill`**, from this app
  and its dev logins (`pnpm dev:accounts`). It holds the feature map
  (`features/`), the helpers that start and check the app, and Playwright
  drivers that sign in as each role, walk the real path and save proof
  (screenshots, aria snapshots, video) under `.verify/` — gitignored.
- A change that touches something a person sees is verified with it before
  the PR, and the PR names the `.verify/<run>/` folder.
- When features change, the owner runs **`/maintain-verification-skill`**
  (pstack; manual-only) so the map follows the app. Its corrections ship as
  one PR; a product regression it finds goes to the owner, never into the
  docs. An agent that changes a feature says in its PR that the map needs
  that pass.

## Shipping a change

Merging to `main` is a production release: CI migrates the production database
and deploys (`.github/workflows/main.yml`). So nothing reaches `main` except
through a pull request the owner has read.

1. **Branch from an up-to-date `main`**, named with a type prefix and a short
   kebab-case description: `fix/…`, `feat/…`, `chore/…`, `docs/…`,
   `refactor/…`. Never commit directly to `main`.
2. **`pnpm check` passes** before every commit, and `pnpm verify` before the
   pull request — plus the verification skill's drive when the change is
   visible. Say so if any was skipped or failed; do not commit around it.
3. **Commit only what belongs to the change.** Stage files by name, not
   `git add -A`.
4. **Commit messages read like the history:** a plain sentence as the title
   saying what is now true (no `fix:`/`feat:` prefixes), then a body explaining
   why — the cause, the decision, what was checked. Not a list of files.
5. **Open a PR against `main`.** The description says what changed, why, and
   how it was verified.
6. **Stop at the PR link.** The owner reviews and merges; agents do not merge.

## Writing code here

- Comments say **why**, in full sentences: the constraint, the incident, the
  decision. What the code does is the code's job.
- User-facing copy is in Spanish, short and plain, and says what to do next.
- Import with `@/`. Files are kebab-case; components PascalCase.
- One `getSession()` per request (it is `cache()`d); one `orgScope()` per
  organization per request (also cached).
